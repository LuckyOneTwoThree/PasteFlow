## 1. 项目元信息与核心定位 (Project Metadata)

### 1.1 基本信息

|属性|定义内容|
|---|---|
|**项目名称**|**PasteFlow**（中文代号：**灵贴**）|
|**一句话 Pitch**|_Don't just copy and paste. Transform in-flight._（懂你正在用什么软件的"自动挡"智能剪贴板）|
|**产品本质**|跨平台操作系统级数据清洗与流转中间件（OS-Level Context-Aware Clipboard Middleware）|
|**目标受众**|**大众层（80%）：** 日常重度使用办公软件、AI 助手、浏览器的白领、运营、学生、财务人员。<br>**极客层（20%）：** 全栈开发者、AI 工程师、效率工具控、开源社区贡献者。|
|**首发平台**|**macOS 优先**（v0.1.0 仅 macOS）。Windows 于 v0.2.0 跟进。依据见 §0.2 G2 与 §9。|
|**核心差异化**|**持有式延迟供给（Owned Lazy Provision）**：PasteFlow 不改写剪贴板，而是*持有*剪贴板并声明全部格式通道，由各消费方按需拉取对应通道——用户按的仍是原生 `Cmd/Ctrl+V`，而 Word 拿到富文本、Terminal 与微信拿到原始文本，**自动挡链路零键盘钩子、零权限申请**。<br>_⚠️ v1.2 措辞收敛：_ "零权限"仅指 **Tier 0**（§3.7）；"原始内容无损"须限定为"经 §8.9 格式保全护栏后有损可控"，不得作为无条件承诺对外传播（§0.1 I2）。|

### 1.2 差异化边界的诚实声明

v1.0 声称"首创三位一体交互"。经竞品核实，该表述**不可用于对外传播**（详见 §9）。可声称的差异化限定为以下四条：

1. **首个以「持有式延迟供给」在原生 `Cmd/Ctrl+V` 上实现零钩子、多格式按需分发的开源剪贴板中间件。** 现有工具要么在复制时急切改写（CopyQ、ClipboardFusion），要么走备用快捷键（PowerToys Advanced Paste、PasteMD）。
   > _⚠️ v1.2 措辞收敛（§0.1 I1 / I2）：_ v1.1 此条含"零权限、无损"两个绝对化表述，均须限定——
   > - **"零权限"限定于 Tier 0**（§3.7）：自动挡主链路 + `⌘C⌘C` 走 `changeCount` 差分检测 + HUD 贴鼠标定位 + 结果写回剪贴板由用户自行 `⌘V`。Tier 1（精确 caret、自动注入、L3 打字机）需 Accessibility，**不得**在对外传播中笼统宣称"零权限"。
   > - **"无损"限定为"经 §8.9 护栏后有损可控"**：接管动作本身会调用 `clearContents()`，实测使源应用声明的 12 个 type 归零（附录 A.7）。我们能保全的是**可直通注册的合法 UTI**；无法保全的是 legacy 4 字符 flavor。因此正确表述是"我们**从不改写用户复制的内容本身**，且在无法完整保全源格式时**放弃接管**"。
2. **首个跨 macOS + Windows 的开源*转换型*剪贴板。** PasteMD 与 Advanced Paste 仅有 Windows；Maccy 仅有 macOS 且只做历史。
3. **首个「一句话生成声明式滤镜配方」（AI Pipe Builder）。** 社区宏库概念 ClipboardFusion 已有，自然语言生成在此品类中未见。
4. **首个在收集槽消费时做 AI 聚合整理。** 收集槽/合并粘贴本身已存在（Ditto Auto Merge、CopyQ Join Selected Items、Paste Pinboards），AI 聚合层未见。

## 2. 核心设计原则 (Design Principles)

后续任何子文档与代码实现必须严格遵循以下 **7** 条铁律（v1.0 为 5 条；v1.1 新增第 5 条并重排序；**v1.2 新增第 7 条，并修订第 1、5 条**）：

1. **零权限开箱即用 (Zero-Permission Out-of-the-Box)** — _v1.2 修订_
   核心高频功能必须基于本地确定性算法（L1）与系统原生 OCR（L2）实现，用户下载安装后第 1 秒**无需联网、无需注册、无需配置 API Key、无需授予任何系统权限**即可完整体验核心爽感。
   > _v1.1 修订说明：_ v1.0 写作"零配置"，但在键盘钩子路线下该承诺**不可能兑现**（macOS 需 Input Monitoring + Accessibility，且无法上架 MAS）。改为持有式延迟供给后，此原则**首次真正可达成**——这是 v1.1 架构变更最重要的收益。
   >
   > _⚠️ v1.2 边界修正（§0.1 I1）：_ v1.1 把"零权限"当成**产品级**属性来宣称，但 §10.1 的 MVP 明确包含 Micro-HUD，而 HUD 的三件事各自需要权限：`⌘C⌘C` 按键序列检测（若走 CGEventTap 则需 Input Monitoring）、caret 精确定位（AXUIElement → Accessibility）、enigo 注入（CGEventPost → Accessibility）。
   > **修正方式不是放弃承诺，而是把它分层并落到可实现的机制上（§3.7）：**
   > - 实测确认 `⌘C⌘C` **可以完全不依赖 event tap**——同一内容连续复制时 `changeCount` 依然自增（附录 A.9），靠差分即可识别双击复制，零权限。
   > - HUD 定位在无 Accessibility 时回退到鼠标坐标（`NSEvent.mouseLocation`，零权限），即 §8.4 的第 2 级。
   > - 注入改为"结果写回剪贴板 + 提示用户自行按 `⌘V`"，零权限，代价是多一次按键。
   >
   > 由此 **Tier 0 真正达成 0 项权限申请**；Tier 1 能力须显式开启。对外传播时必须带上"自动挡链路"或"Tier 0"限定词。

2. **肌肉记忆零妥协 (Zero Muscle-Memory Friction)**
   绝不破坏用户几十年养成的原生 `Ctrl/Cmd + C` 与 `Ctrl/Cmd + V` 习惯。**任何会给日常粘贴增加可感知延迟的设计一律否决**——据此删除 `Ctrl+V+V` 触发通道（§0.2 C1）。
   > _v1.2 补充：_ 此原则同时否决了"在 provider 回调里跑 L2 OCR"（§0.1 I4）。回调内 100ms 已是可感知延迟，13.5s 冷启动等于挂死宿主应用的 `⌘V`。

3. **无焦点抢占 (Non-Activating UI)**
   任何悬浮提示、光标微胶囊弹出时，绝对不能抢夺当前活动窗口的输入焦点。
   > _v1.1 补充：_ 此原则在两端实现路径**不对称**，不得假设同一套代码（§0.2 C3）。

4. **本地隐私绝对优先 (100% Local-First & Privacy Guard)**
   所有剪贴板历史仅存储于本地 SQLite；内置不可关闭的密码管理器进程黑名单；支持在发送给外部 AI 前自动执行本地正则脱敏（DLP）。
   > _⚠️ v1.2 补充（§0.1 I13）：_ 本原则**优先级高于原则 5**。当内容命中 `contains_secret` 时，脱敏结果必须覆盖**全部三个通道**，且原始明文**不得**通过任何 UI 路径回贴。详见原则 5 的安全例外与 §8.7。
   > _v1.2 新增告知义务（§8.10）：_ 持有式架构下，转换结果可能被 Universal Clipboard 同步至用户的其他 Apple 设备。此行为须在首次接管时明确告知，不得静默发生。

5. **原始内容不主动销毁 (Non-Destructive by Default)** — _v1.1 新增，v1.2 修订标题与边界_
   PasteFlow **从不改写用户复制的内容本身**；原始数据始终由本进程持有，并可通过 HUD / 抽屉"粘贴原始内容"取回。
   > _依据：_ v1.0 的"原地重写剪贴板"违反此原则（§0.2 B3）。持有式延迟供给在架构上满足"不改写"。
   >
   > _⚠️ v1.2 诚实修正（§0.1 I2）：_ v1.1 写作"原始内容**无损**"并称"持有式延迟供给在架构上**天然满足**"。**这是过度承诺。** 实测：接管动作本身必须调用 `clearContents()`，源应用声明的 **12 个 type 全部归零**，Chrome `org.chromium.source-url`、Excel 私有 UTI 等一并销毁（附录 A.7）。直通机制能救回**合法 UTI**，但**救不回 legacy 4 字符 flavor**——对只使用 legacy flavor 的源应用，强行接管会导致剪贴板 `types=[]`、**什么都粘不出来**，比不接管更糟。
   > **⇒ 本原则的正确表述是：不主动销毁 + 无法完整保全时放弃接管（§8.9 G1–G4），而非承诺无损。**
   >
   > _⚠️ v1.2 安全例外（§0.1 I13，**不可协商**）：_ 命中 `contains_secret` 的条目**不适用**本原则的回贴能力——
   > - `html` / `rtf` / `plainText` **三个通道全部输出脱敏结果**，无一例外；
   > - `preserveOriginal` 强制为 `false`；
   > - HUD 与抽屉的「粘贴原始内容」对该条目**置灰**，并显示原因；
   > - 原始明文可留存于本地 SQLite 供用户自查（原则 4 的本地优先），但**不存在任何把它写回剪贴板的路径**。
   >
   > _理由：_ v1.1 §4.2 要求"**始终**包含「粘贴原始内容」"，与 §8.7 的 DLP 红线正面冲突。持有式架构使这个洞比 v1.0 **更大**——v1.0 原地重写后明文物理上就消失了，v1.2 却主动把明文保存在进程内并承诺一键可取回。DLP 滤镜若只改通道而保留回贴入口，等于没做。

6. **声明式可扩展 (Declarative Extensibility)**
   所有转换能力抽象为标准化 `PipeRecipe`，支持单文件 JSON/YAML 或自然语言一句话生成，便于社区提交 PR。
   > _v1.2 补充（§0.1 I9）：_ 配方文件是**机器消费的协议**且将被社区当模板抄写，因此**严禁**在 JSON 内夹带 `*_note` 一类编辑期批注字段。所有说明写入本文档正文与 JSON Schema 的 `description`，Schema 须设 `additionalProperties: false`。

7. **宁可不接管，不可破坏原生粘贴 (Never Degrade Native Paste)** — _v1.2 新增_
   任何一次"接管剪贴板"的决定，都必须以"用户的 `⌘V` 仍能粘出**至少与不接管时等价**的内容"为前提。**当这个前提无法保证时，必须放弃接管**，退回系统原生剪贴板行为。
   > _为什么需要这条原则：_ v1.1 的边界条件缺陷（legacy flavor 直通失败、多 item 压平、L2 冷启动阻塞、进程退出数据蒸发）**共享同一个失败形态**——用户按 `⌘V`，什么都没发生，或发生了错的事，而且**我们收不到任何错误信号**。这类故障对产品信任的伤害远大于"某次没有自动净化"。
   > _如何应用：_ 本原则是**所有未枚举边界情况的默认裁决依据**。下游 Agent 遇到本文档未覆盖的接管场景时，一律选择放弃接管，并在 §11.4 诊断面板中记录原因，而不是自行发明乐观路径。具体护栏见 §8.9。

## 3. 核心架构决策：持有式延迟供给 (Owned Lazy Provision)

> **本节为 v1.1 新增，是整个产品的架构地基。所有下游文档与实现必须以此为准。**

### 3.1 问题：v1.0 的拦截式架构为何不可行

v1.0 设计的链路是：`监听 Ctrl/Cmd+V` → `<1ms 内取焦点窗口` → `匹配 AutoRule` → `原地重写剪贴板多格式缓冲区` → `放行原生粘贴`。

该设计把产品成败压在操作系统最脆弱的一环上，已核实的失败模式：

- **钩子静默失效**：回调超过 `LowLevelHooksTimeout` 后，系统放行消息，且 Win7+ **静默卸载钩子，应用无法感知**。用户会遇到"自动挡莫名不工作了"，而我们收不到任何信号。
- **与官方指引冲突**：微软明确建议低阶钩子应在专用线程上**立即返回**、把工作交给后台线程。而本设计**必须**在钩子内同步完成重写才能保证目标应用读到新内容——两者不可调和。
- **杀软误报**：`WH_KEYBOARD_LL` 安装器被 Defender/赛门铁克标记为木马，对开源项目的安装转化是致命的。
- **破坏性重写**：原始内容丢失（原则 5）。
- **读取竞态**：剪贴板是全局互斥资源。已有公开复盘记录：在异步读取方（如 Paint）读取过程中改写剪贴板，会触发模态错误 `operation did not succeed`；正确解法是 `OleSetClipboard` + 引用计数 `IDataObject`，**而非原地重写**。
- **权限墙**：macOS 需 Input Monitoring + Accessibility，无法上架 MAS，且撤销权限时有 active event tap 会导致系统级输入卡死。

### 3.2 解法：让操作系统的格式协商替我们做"目标应用感知"

**核心洞察：绝大多数场景下我们根本不需要知道 `TargetApp` 是谁。**

在复制发生的那一瞬间，PasteFlow **持有**剪贴板（而非改写它），声明所有可用格式通道；当某个应用来读取时，按它请求的通道**现场计算**并返回对应内容：

- Word / 飞书 / 钉钉文档 / WPS 请求 `public.html`（或 `CF_HTML` / `CF_RTF`） → 得到带原生标题、加粗、表格的富文本
- 微信 / 终端 / VSCode / 记事本 请求 `public.utf8-plain-text`（或 `CF_UNICODETEXT`） → 得到清洗后的纯文本

**"目标软件感知"由操作系统的格式协商自动完成，无需钩子、无需权限、无需在 1ms 内做任何事。**

|---|---|---|
|**同一通道只能有一份内容**|"微信要美化纯文本"与"IDE 要原始 markdown"都请求 `plain-text`，无法靠通道区分|**v1.2 定案：** 引入 `plainTextPolicy` per-filter 枚举（§5.4），默认 `PASSTHROUGH`。辅以①保守触发阈值 ②按滤镜开关 ③HUD「粘贴原始内容」④真正按目标应用分支留作进阶模式（§3.6）|
|**不注册 plainText 通道 ≠ 保留原始内容**|⚠️ **实测陷阱（附录 A.10）**：只注册 `html`/`rtf` 而不注册 `plainText` 时，AppKit 会**从 RTF 自动合成**纯文本，消费者读到的是 `TRANSFORMED-RTF`——转换结果泄漏进纯文本通道|**必须显式注册 `public.utf8-plain-text` 并提供我们自己的值**。实测确认显式 provider **优先于** AppKit 合成。此为 §5.4 `PASSTHROUGH` 策略的实现前提|
|**macOS 无法识别请求方**|`provideDataForType` 不提供调用方进程信息（实测确认，附录 A.9）|接受。macOS 上不做目标应用分支。**连带后果：无法确知粘贴是否发生 → Toast 必须移到接管时（§4.1 步骤 4）**|
|**接管理论上有损**|`clearContents()` 会销毁源应用声明的全部 type；legacy 4 字符 flavor **无法**通过 `setDataProvider` 直通（实测 `types=[]`、数据不可读）|§8.9 直通机制 + **接管前置护栏 G1–G4**。核心裁决依原则 7：保不全就不接管|
|**多 item 剪贴板会被压平**|⚠️ **实测（附录 A.11）**：复制 2 个文件后 `pasteboardItems.count=2`，用单 item 接管后塌成 `1`|§8.9 护栏 G2/G3：`count > 1` 或含 `public.file-url` 一律放弃接管|
|**provider 进程退出 → 数据蒸发**|⚠️ **实测（附录 A.8）**：owner 退出后 `changeCount` 不变、剪贴板看上去仍是满的，但 `types=[]`、读到 `nil`。用户退出 / 崩溃 / 被系统杀掉后 `⌘V` **粘不出任何东西**|§8.8 急切物化：宽限期（建议 1s）后把所有已声明通道写为真实数据，并在 `applicationWillTerminate` 无条件物化一次。修法已实测验证通过|
|**剪贴板所有权会被夺走**|用户在其他应用复制会调用 `clearContents`，我们的 provider 随之失效|监听 `changeCount`（macOS）/ `WM_CLIPBOARDUPDATE`（Windows），所有权丢失时优雅降级并清理状态（§8.2）。**v1.2 补充：物化前必须校验所有权仍在我方**（§8.8）|
|**Universal Clipboard / Handoff 会拉走 provider**|`sharingd` 代表 Handoff 读取剪贴板以同步到 iPhone/iPad。后果：①转换结果被推送到用户其他设备 ②其回调等待容忍度未知，L2 冷启动必超时|§8.10。**列为 Step 0 spike 必测项**（§12）。首次接管时须明确告知用户此行为（原则 4）|
|**Windows 可能可以识别请求方**|COM 服务端理论上可经 `IServerSecurity::ImpersonateClient` 取得调用方 PID，从而实现真正的目标应用分支|**⚠️ 未验证**，列为 v0.2.0 研究 spike（§10.2）。若成立，Windows 版反而能获得 macOS 拿不到的能力|

### 3.6 可选进阶模式：目标应用分支（Opt-in Auto-Pilot Pro）

对确实需要"同一通道、不同目标、不同内容"的用户，提供**显式开启**的进阶模式，走键盘钩子 + 焦点窗口识别路线。

设计约束：
- 默认**关闭**，开启前必须完整告知权限要求与杀软误报可能性
- 采用**复制时预计算 + 粘贴时 O(1) 查表**：复制瞬间就为各候选目标应用预渲染并缓存（键为 `contentHash × targetApp`），使钩子内只做「取前台窗口 → 哈希查表 → 单次剪贴板写入」，把在钩子内的耗时从 O(转换) 降到 O(1)，尽量贴合超时预算
- 钩子线程必须立即返回，任何 I/O 与转换均在后台线程完成（遵循微软指引）
- 必须实现钩子健康自检与自动重装，并在 UI 中暴露状态（§11.4）——因为系统静默卸载时应用无法感知

### 3.7 权限分层：Tier 0 / Tier 1（v1.2 新增）

> _为什么需要本节：_ v1.1 把"零权限"当作**产品级**属性宣称，但 MVP 范围内含 Micro-HUD，而 HUD 的按键检测、caret 定位、结果注入分别需要 Input Monitoring / Accessibility。**这不是承诺造假，而是承诺没有分层**——修正方式是把每一项能力明确归入某一档，并给出零权限档的替代实现路径。

| 能力 | Tier 0（**零权限，默认**） | Tier 1（需 **Accessibility**，显式开启） |
|---|---|---|
| **自动挡主链路**（§4.1） | ✅ 完整可用。`NSPasteboard` 读写不需要任何 TCC 权限 | — |
| **`⌘C⌘C` 双击检测** | ✅ **不用 event tap**。实测：同一内容连续复制时 `changeCount` 依然自增（28→29→30，间隔 0.18ms，附录 A.9）。判定条件见下方 | ✅ 可选：CGEventTap 路径（需 Input Monitoring），精度更高但**不作为默认** |
| **`⌃⌥V`（mac）全局热键** | ✅ `RegisterEventHotKey` 不需要 Input Monitoring | — |
| **HUD 定位** | ✅ 回退至鼠标坐标 `NSEvent.mouseLocation` + `(12px, 12px)` 偏移，即 §8.4 第 2 级 | ✅ 精确 caret：`AXUIElement` → `kAXSelectedTextRange` → `kAXBoundsForRangeParameterizedAttribute` |
| **HUD 结果上屏** | ✅ **写回剪贴板 + 提示用户自行按 `⌘V`**（多一次按键，零权限） | ✅ `enigo` / `CGEventPost` 自动注入（零额外按键） |
| **L3 打字机流式** | ❌ 不提供（必须注入） | ✅ 提供，且须遵守 §5 L3 的安全栏 |
| **目标应用分支（§3.6）** | ❌ 不提供 | ✅ 提供（Windows 侧另需钩子） |

**`⌘C⌘C` 的 Tier 0 判定条件（三个条件必须同时满足，缺一即视为普通复制）：**

1. `changeCount` 在 **250ms** 内自增 ≥ 2 次
2. 前后两次的 `contentHash` **完全相同**
3. 前后两次的 `SourceApp` **完全相同**

> _为什么条件 2、3 不可省：_ 仅凭"250ms 内两次自增"会误触发——用户在两个不同应用间快速复制两段不同内容、或某些源应用对单次 `⌘C` 做两阶段写入（先写后更新），都会产生同样的信号。加上同 hash + 同 SourceApp 后，误触发面收敛到"用户真的重复复制了同一段内容"，而这恰好是幂等无害的。
>
> _⚠️ 实现注意：_ 若第一次 `⌘C` 已被我方接管，第二次 `⌘C` 会让源应用调用 `clearContents` → 我方 `changeCount` 前进 → **§8.2 会判定为所有权丢失**。因此本检测必须挂在所有权状态机**之前**，或让状态机识别"新内容与当前持有内容同 hash"这一特例，否则第二次复制会被当成普通的顶替处理，双击永远触发不了。

**Tier 切换的产品要求：**

- 安装后默认 **Tier 0**，全功能可用（除 caret 精度与自动注入）。**首次启动不出现任何权限弹窗**，兑现原则 1 与 §4.4 的破冰承诺。
- Tier 1 必须由用户在设置里**主动开启**；开启前完整告知：需要哪些权限、为什么、以及 macOS 上撤销 Accessibility 时若存在 active event tap 可能导致系统级输入卡死（§0.2 B4）。
- **MAS 上架可行性仅限 Tier 0 构建**。即便 Tier 0 不含钩子，MAS 沙盒是否允许长时间持有 `NSPasteboard` 所有权**尚未验证**，列为 §11.2 的待确认项，不得预先宣称"可上架 MAS"。

## 4. 核心交互形态与键盘状态机 (Interaction & Input State Machine)

### 4.1 交互面一：场景感知"自动挡" (Silent Auto-Pilot)

- **触发条件：** 用户在任意应用执行普通的 `Ctrl/Cmd + C`，随后在目标应用执行普通的 `Ctrl/Cmd + V`。**两个按键均不被拦截。**

- **系统行为（v1.2 修订）：**

    1. **复制阶段（Capture & Own）：** 监听到剪贴板变动，Rust 后端读取内容并记录复制源窗口进程信息 `SourceApp` 与内容特征标签 `ContentTags`（如 `is_markdown`、`is_dirty_html`、`is_tracking_url`、`has_secret`）。
       > _⚠️ v1.2 修正（§0.1 I8）：_ v1.1 未指定 `SourceApp` 的获取机制。这不是小事——在持有式架构下 `SourceApp` 已从"辅助元数据"升级为**唯一**的应用感知信号（§7.2 `matchSourceApps`，因为 `TargetApp` 已不再获取），轮询误差的后果从"记录不准"变成"**滤镜误匹配**"。典型竞态：用户在 Chrome 里 `⌘C` 后立刻 `⌘Tab` 切到 Word，若 watcher 靠轮询 `changeCount`（通常 100–500ms 一次）才去查 `NSWorkspace.shared.frontmostApplication`，拿到的会是 **Word** 而非 Chrome。
       >
       > **强制方案（事件驱动，禁止轮询取前台应用）：** 订阅 `NSWorkspace.didActivateApplicationNotification`，把 `(bundleId, timestamp)` 持续写入一个小的环形缓冲（建议 16 槽）；`changeCount` 自增时，取**时间戳早于自增时刻且最接近它**的那条记录作为 `SourceApp`。Windows 侧对应 `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` + `GetClipboardSequenceNumber()`。
    2. **判定与持有（Own）：** 先过 **§8.9 接管前置护栏 G1–G4**（v1.2 新增，任一不通过即放弃接管）；通过后，若内容命中任一激活滤镜且置信度达 `minConfidence`，PasteFlow **接管剪贴板所有权**，声明全部输出通道（`html` / `rtf` / `plainText`），并将原始内容完整保留在进程内。
    3. **粘贴阶段（Lazy Provision）：** 用户按原生 `Ctrl/Cmd + V`。目标应用向剪贴板请求它偏好的格式，provider 被调用，**此刻才执行对应的 L1 转换**并返回结果。
       > _⚠️ v1.2 强制约束（§0.1 I4，**本版最高危修正**）：_ v1.1 此处写作"执行对应的 **L1/L2** 转换"，§6.4 数据流图更在回调内部画了 `[L2 Engine 热态 <100ms]`。**必须禁止。** provider 回调运行在**宿主应用（Word / 微信）的粘贴请求上下文**中——回调耗时多久，用户的 `⌘V` 就卡多久。而 L2 的机器级首次调用实测 **13,554ms**（附录 A.2），在回调里跑等于挂死宿主应用，且**我们收不到任何错误信号**，用户只会看到 Word 转圈。
       >
       > **规则：provider 回调内只允许 L1，且设 8ms 硬超时；超时或异常一律返回原始内容（§8.11）。L2/L3 必须移出主链路**——走"复制后后台预热 + HUD 手动触发 + 结果写回剪贴板"。
    4. **视觉微反馈：** **接管完成的瞬间**（而非粘贴后）浮现无焦点半透明胶囊 Toast（停留 `800ms` 淡出）。
       > _⚠️ v1.2 修正（§0.1 I5）：_ v1.1 要求在"粘贴完成后"出 Toast，文案为 `✨ 已自动净化为 Word 标准排版`。问题：**macOS 上无法确知粘贴是否发生**——`provideDataForType` 不携带调用方身份（附录 A.9 实测确认），我们无法区分"用户真的粘贴了"与"Finder 快速查看 / Alfred / Handoff 的 `sharingd` 顺手拉了一下"。按 v1.1 实现必然产生**幽灵 Toast**（用户从未粘贴却看到"已净化"）。
       >
       > **修正方式是从构造上消灭问题，而非靠启发式过滤**：反馈时机移到接管时——这是一次真实发生、我们完全掌握的事件。文案改为分通道预告，信息量反而更大：
       > `✨ 已就绪 · 富文本应用将收到排版结果 · 纯文本应用将收到原文`
       > 800ms 淡出、无焦点、不抢占输入等约束照旧（原则 3）。

> _v1.1 修订说明：_ v1.0 的步骤 2「粘贴阶段（Intercept & Morph）」要求在 `<1ms` 内取焦点窗口并原地重写。v1.1 已将该逻辑整体移至复制阶段，粘贴阶段不再有任何拦截行为。

### 4.2 交互面二：光标微胶囊"手动挡" (Cursor Micro-HUD)

**触发通道（v1.2 修订）**

|通道|按键|状态|Tier|说明|
|---|---|---|---|---|
|A（源端双击复制）|按住 `Ctrl/Cmd` 连续双击 `C`（间隔 `< 250ms`）|✅ **默认主推**|**Tier 0**|重复复制幂等、零副作用。**v1.2：macOS 上无需 event tap**，靠 `changeCount` 差分即可检测（判定三条件见 §3.7）|
|B（目标端呼出）|macOS：`⌃⌥V`（Control+Option+V）<br>Windows：**`Ctrl+Alt+V`**|✅ 备选|**Tier 0**|**v1.2 修正：Windows 侧由 `Alt+Shift+V` 改为 `Ctrl+Alt+V`**，因与 §4.3 抽屉撞车（§0.1 I6）。全局热键注册不需要 Input Monitoring|
|~~C~~|~~`Ctrl/Cmd+V+V` 双击~~|❌ **已删除**|—|第一次 `Ctrl+V` 已贴出原始内容。要么忍受"贴错再改"的视觉闪烁与不可靠的撤销，要么给**每一次**日常粘贴加 250ms 延迟——两者均违反原则 2|

> **按键冲突依据（v1.1 新增，v1.2 补全）：**
> - macOS `Option+V` 系统级映射为 `√`（平方根）。v1.0 将其设为"默认主推"，实际使用时会向文档插入 `√` 字符；要吞掉该按键必须使用 active event tap，而这需要 **Accessibility** 权限（listen-only 的 Input Monitoring 不够）。故 macOS 改用 `⌃⌥V`。
> - Windows 上 `Alt` 单独按下会在 Office 中激活功能区 KeyTips；`Alt+V` 在部分应用中有既有绑定。
> - **⚠️ v1.2 修正（§0.1 I6）：** v1.1 把 Windows HUD 定为 `Alt+Shift+V`，与 §4.3 抽屉的 `Alt/Opt+Shift+V` **完全撞车**。v1.1 line 210 自己写了"需在实现时消歧或分别指定"却把问题推给了下游——两份文档同时被喂给 Coding Agent 时，它会随机挑一个。**v1.2 定案：Windows HUD = `Ctrl+Alt+V`，抽屉 = `Alt+Shift+V`。** 完整登记表见 **§4.5**，该表为快捷键的唯一真源。

**UI 形态与行为**

- 紧贴当前文本输入光标（Caret Position，取不到则回退至鼠标指针）弹出毛玻璃微胶囊菜单（宽 `260px`，最多 4 个智能推荐动作）。
- **动态上下文推荐：** 菜单项根据当前 `ContentType` 动态生成（见 §5）。
- **极速上屏（v1.2 修订）：** 按数字键 `1~4`、`Enter` 或鼠标点击后：
    - **L1/L2 本地转换 → 默认走「原子粘贴」**：结果一次性写入剪贴板，随后触发单次 `⌘V`（Tier 1 自动注入）或提示用户自行按 `⌘V`（Tier 0）。
    - **L3 AI 流式 → 默认同样走原子粘贴**（等待完整结果后一次写入），HUD 期间显示呼吸灯态 `⚡ 正在转换...`。
    - **打字机分块输出降级为 opt-in**，且必须实现 §5 L3 的三条安全栏。
      > _⚠️ v1.2 修正（§0.1 I14）：_ v1.1 把"模拟打字机/分块方式输出"写成 L3 的默认行为。该行为有三个未识别的问题：① 需要持续注入，中途用户 `⌘Tab` 切窗口，剩余文本会被**喷洒进错误的应用**——若内容含已脱敏的敏感上下文，这是**数据泄漏而非 UX 问题**；② 逐字符注入会把目标应用的**撤销栈打碎**，用户一次 `⌘Z` 撤不掉整段；③ 逐字符注入在中文输入法下存在被 IME 拦截的风险（注：`enigo` 走 `CGEventKeyboardSetUnicodeString` 直接插入 Unicode，此风险低于 v1.1 审查的估计，但前两条足以否决默认地位）。
- **菜单项「粘贴原始内容」（v1.2 修订）：** 默认始终包含，兑现原则 5。
  > _⚠️ v1.2 例外（§0.1 I13，**不可协商**）：_ v1.1 写作"**始终**包含"，与 §8.7 的 DLP 红线正面冲突——命中 `contains_secret` 的条目，若通道已脱敏但此处仍能一键取回明文，DLP 等于没做。而且持有式架构让这个洞**比 v1.0 更大**：v1.0 原地重写后明文物理上就消失了，v1.2 却主动把明文保存在进程内并承诺可取回。
  > **规则：** 命中 `contains_secret` 时该项**置灰**并显示原因（`🔒 含敏感信息，原文回贴已禁用`）；`preserveOriginal` 强制 `false`；三通道全部输出脱敏结果。详见原则 5 安全例外与 §8.7。

> **⚠️ 跨平台不对称（v1.1 新增，必须实现时区分）**
> - **macOS：** `NSPanel` + `NSWindowStyleMaskNonActivatingPanel` 可在**不激活应用**的前提下成为 key window，从而直接接收 `1~4`/`Enter`。
> - **Windows：** `WS_EX_NOACTIVATE` 能使窗口不被激活，但**无法获得键盘焦点**，因此 HUD **收不到**任何键盘消息。数字键与 Enter 必须由全局钩子捕获后转发给 HUD 状态机。
> - 结论：两端的键盘输入路径必须分别实现，不得假设对称。

> **⚠️ HUD 渲染方式与内存指标的冲突（v1.1 提出，v1.2 已决议）**
> v1.0 要求 `micro-hud` "常驻隐藏、0ms 唤醒"，同时要求常驻内存 `< 25MB`。二者不可兼得：
> - 常驻 webview → 实测整应用空闲 private 183–199MB（Windows WebView2，附录 A.5），远超 25MB
> - 按需创建 webview → 100–300ms 冷启动，做不到"0ms 唤醒"
>
> **✅ v1.2 决议（D1，见附录 B）：采用方案乙——常驻一个隐藏 Tauri `WebviewWindow`。**
> 理由：MVP 排期 3–4 周，方案甲要求同时维护 AppKit/CoreText 与 Direct2D/WinUI 两套原生 UI，会直接击穿排期；而 HUD 只有 4 个菜单项，webview 的开销是可接受的成本。
> **配套约束：**
> 1. §1.3 内存指标已拆为两行——"Rust 核心进程 `< 25MB`（不含 webview）"与"整应用空闲内存（**待 Step 0 spike 实测后填数**）"。
> 2. **不采纳审查建议的 `<100MB` 目标值**：现有唯一实测数据来自 Windows WebView2，macOS WKWebView 本机未测。在拿到实测数之前写死目标，会让下游 Agent 把一个未验证的数字当验收标准。
> 3. 常驻 webview 必须**真的隐藏且不加载路由**（`visible: false` + 空白页），仅在首次呼出时注入内容；否则"常驻"会连带常驻一整套 React 运行时。

### 4.3 交互面三：磁吸式"历史与贪吃蛇"抽屉 (History & Stack Drawer)

- **触发方式：** `Alt/Opt + Shift + V`（macOS `⌥⇧V` / Windows `Alt+Shift+V`），或鼠标停靠屏幕边缘。
  > _v1.2：_ 本键位已在 **§4.5 快捷键全局登记表**登记（Tier 0，`RegisterEventHotKey` / `RegisterHotKey`，不需要 Input Monitoring）。**§4.5 为唯一真源**，此处与 §4.5 冲突时以 §4.5 为准。

- **模块 A — 时间轴历史（Timeline）：** 全文毫秒级搜索（SQLite FTS5）、按类型过滤（文本/图片/链接/代码/文件）、常用项置顶（Pin）。
  > _v1.2 修正（§0.1 I7）：_ v1.1 此处要求"每条历史记录**必须同时保存原始内容与各通道转换结果**"。这与延迟供给直接矛盾——复制那一刻通道产物**还不存在**（§6.4 明确"此刻【不】执行任何转换"，§7.1 的 `status` 初值为 `'pending'`）。

    - 抽屉顶部设醒目【🐍 贪吃蛇连续收集】开关（快捷键 `⌥⇧S` / `Alt+Shift+S`，已登记于 §4.5）。

    - **一键消费**，三种输出模式：
        1. **换行拼接：** 用换行符或分割线合并所有片段一次性粘贴。
        2. **去重编号：** 剔除重复行并生成 `1. 2. 3.` 有序列表。
        3. **AI 聚合整理（差异化重点）：** 将 N 个碎片作为上下文喂给 L3，直接输出结构化会议纪要、竞品分析表或周报。

## 5. 三级引擎能力矩阵 (3-Tier Processing Engine Matrix)

系统严禁将所有任务丢给大模型。所有剪贴板处理按以下三级漏斗路由：

### L1：本地闪电引擎 (Deterministic Local Engine)

|项|内容|
|---|---|
|**定位**|耗时 `< 5ms`；占日常使用 70%；100% 离线、零成本|
|**底层实现**|Rust 原生正则（`regex`）、HTML/Markdown AST 解析（`pulldown-cmark`、`scraper`）、代码结构推断（`serde_json`）|
|**v1.2 执行时机**|在 provider 被调用（消费方拉取某通道）时执行，而非复制瞬间。可选择在复制后异步预渲染并缓存以进一步降低感知延迟|
|**⚠️ v1.2 硬约束**|provider 回调内**只允许 L1**，且受 **8ms 硬超时**约束（§8.11）。超时、panic、任何异常 → **一律返回原始内容**，不得阻塞宿主应用的 `⌘V`。**L1 handler 内严禁任何 I/O**（磁盘、网络、SQLite 写入）；缓存查询只允许命中内存态|

**核心内置滤镜：**

1. **【AI 星号净化器】** 将 DeepSeek/ChatGPT 复制的 Markdown 转为带原生标题、加粗、表格的 Word/飞书富文本（`html` + `rtf` 双通道）。
   > _⚠️ v1.2 修正（§0.1 I3）：_ v1.1 的描述是"…富文本（HTML/RTF 双写）**或微信精致纯文本**"。后半句与 §10.1 的 MVP 成功判据（Terminal 按 `⌘V` **得到原始 Markdown**）**在同一通道上直接互斥**——两者都走 `public.utf8-plain-text`，不可能同时成立。
   > **v1.2 定案：本滤镜 `plainTextPolicy = PASSTHROUGH`**，即纯文本通道输出**原始 Markdown**。理由：① 兑现原则 5；② 失败代价不对称——把美化文本喂给 IDE 是**代码被改坏**（高危），把原始 Markdown 喂给微信只是**少了个增强**（低危）；③ §10.1 的 demo（"Word 得到排版、Terminal 得到原文"）本身就是传播素材，必须默认成立。
   > **"微信精致纯文本"降级为 HUD 手动动作**（一个独立的 `PipeRecipe`，`mode: MANUAL_ONLY`），并在角色卡为 💼/📊/🎓 时默认挂载到 HUD 首位。这样两个场景都能满足，但不再争夺同一个默认值。
   > _⚠️ v1.1 工程警示（保留）：_ 此为旗舰滤镜，也是**最难**的一个。Word 会忽略大部分标准 CSS，需要 `mso-` 专有样式或走 RTF 才能获得保真的标题层级与表格边框；飞书/钉钉/企业微信的 web 编辑器各有自己的粘贴净化器会剥离 HTML；微信桌面端只接受纯文本。**必须建立 §8.5 的兼容性测试矩阵并纳入 CI**，不得凭直觉认为"生成了 HTML 就等于 Word 里好看"。
2. **【网页牛皮癣洗白】** 剥离网页复制的刺眼背景色、字号、内联样式，仅保留语义化段落、加粗与列表。
   > _v1.2：_ `plainTextPolicy = CLEANED`。此处净化是合理的——浏览器对网页复制生成的原始 plainText 本身就夹带导航、广告、"Advertisement"等垃圾，**它不是"用户的原始内容"，而是需要被清洗的对象**。
3. **【PDF 断行缝合】** 自动识别中英文 PDF 复制产生的硬回车断行与连字符，合并为通顺自然段。
   > _v1.2：_ `plainTextPolicy = CLEANED`。原始态就是断的，缝合正是全部价值所在；此滤镜若走 `PASSTHROUGH` 等于不工作。
4. **【社媒链接瘦身】** 剥离淘宝、B站、小红书、京东等分享文本中的追踪参数（`spm=`、`vd_source=` 等）与冗长口令。
   > _v1.2：_ `plainTextPolicy = CLEANED`。剥离追踪参数就是滤镜的全部意义。
   > _v1.1 定位（保留）：_ URL 追踪参数清洗在海外已有成熟方案（StopTheMadness Pro、PlainText），**中文电商/社媒口令清洗才是本地化优势**，应作为中文社区首发的传播点。
5. **【开发者瑞士军刀】** JSON 格式化与转 TS/Go/Python/Rust 类型定义；cURL 转 `fetch`/代码；时间戳与 JWT/Base64 实时解码预览。
   > _v1.2：_ `plainTextPolicy = PASSTHROUGH`，转换结果只走 HUD 手动动作。开发者对"我的代码被自动改了"的容忍度最低，任何自动改写都是负分。
6. **【DLP 隐私脱敏盾】** 自动识别 API Key（`sk-...`）、数据库连接串、私钥、手机号、身份证号，替换为 `<REDACTED>`。
   > _⚠️ v1.2 强制约束（§0.1 I13，**不可协商**）：_ `plainTextPolicy = SANITIZED_FORCED`，语义为：
   > - **三个通道（`html` / `rtf` / `plainText`）全部输出脱敏结果**，无一例外；
   > - `preserveOriginal` 强制 `false`，配方文件里写 `true` 也**必须被运行时覆盖**；
   > - HUD 与抽屉的「粘贴原始内容」对该条目**置灰**并说明原因；
   > - 该滤镜的 `minConfidence` 应显著低于其他滤镜（建议 `0.5`）——**漏脱敏的代价远大于误脱敏**。误脱敏只是让一段普通文本变成 `<REDACTED>`，用户能立刻发现并手动取回；漏脱敏则意味着密钥进了 ChatGPT。
   > - 本地 SQLite 可留存明文供用户自查（原则 4 的本地优先），但**不存在任何把明文写回剪贴板的路径**。
   >
   > _为什么 v1.1 漏了这条：_ v1.1 §4.2 写"**始终**包含「粘贴原始内容」"、§7.2 写 `preserveOriginal: true`，而 §8.7 的红线只覆盖了"复制**源**是密码管理器"的情形，**没有覆盖"普通应用复制出的内容里夹带密钥"**。持有式架构把这个洞放大了：v1.0 原地重写后明文物理消失，v1.2 却主动把明文保存在进程内并承诺一键可取回。

### L2：系统原生视觉引擎 (Native OS Vision Engine)

|项|内容|
|---|---|
|**定位**|**热态** `< 100ms`（v1.0 为 `< 300ms`）；占日常使用 20%；100% 离线|
|**底层实现**|macOS：`Vision Framework`（`VNRecognizeTextRequest`）<br>Windows：`Windows.Media.Ocr`|
|**排期**|**v0.2.0**（v1.0 曾列入 Phase 1 Must，v1.1 移出，理由见 §10.1）|
|**⚠️ v1.2 硬约束**|**严禁进入 provider 回调（§0.1 I4）。** L2 只能走两条路径：① 复制后在后台线程预热并把结果写入缓存（此时若消费方尚未拉取，provider 可在 8ms 内命中缓存返回）② HUD 手动触发 + 结果写回剪贴板。**回调内绝不能同步等待 OCR**：机器级首次调用实测 13,554ms，足以挂死宿主应用的 `⌘V`，且我方收不到任何错误信号|

**v1.1 实测修正（本机 macOS 27.0.1，详见附录 A.2 / A.3）：**

- ✅ **中文零配置可用**：`recognitionLanguages = ["zh-Hans", "en-US"]` 直接识别成功，无需安装任何语言包。macOS 侧"零配置"承诺成立。
- ⚠️ **必须使用 `.accurate`**：`.fast` 模式耗时相近（50ms）但**仅识别出 6/10 个文本块，会丢单元格**，不可用于表格还原。
- ⚠️ **首次调用极慢**：机器级首次调用实测 **13,554ms**（模型资产 materialization）；新进程首次 171ms；热态 52–70ms。
  → **强制要求：** 应用启动时后台预热 OCR 引擎；预热完成前触发 OCR 必须显示明确 loading 态与预计耗时，否则用户首次截图会判定软件卡死。
- ❌ **Windows 侧"零配置"不成立**：`Windows.Media.Ocr` 依赖 `Language.OCR*` 系统能力包，大量语言处于 `State: NotPresent`，`OcrEngine.TryCreateFromLanguage` 会返回 `null`（PowerToys Text Extractor 即会报"没有安装可能的 OCR 语言"）。
  → **强制要求：** 启动时探测 `AvailableRecognizerLanguages`；目标语言缺失时优雅降级（提示用户安装语言包并给出指引，或提供可选的本地模型兜底——注意这会突破 10MB 安装包指标，须权衡）。

**核心内置滤镜：**

1. **【截图秒变 Excel】** 识别图片中文本块与坐标边界框，按行列对齐还原为 TSV 或 Markdown Table，贴入 Excel 自动分列。
   > _⚠️ v1.1 重大修正：_ v1.0 将其描述为"配合本地二维坐标聚类算法还原表格行列"，**严重低估难度**。实测证据：
   > - 同一行内各 observation 的 y 值不齐（`0.631` vs `0.617`；`0.455` / `0.463` / `0.448`），朴素的 y 相等分组必然失败，需 **y 重叠容差聚类**。
   > - 跨列文本会被合并为**单个** observation：实测中"灵贴 PasteFlow 张三"横跨 `x=0.033, w=0.233`，覆盖了第 1、2 列的边界，按 x 聚类会错误归列；而该行的数值 `120,000` 是**另一个独立** observation（`x=0.300, y=0.617`）。
   > - 无边框表格的列边界必须从**所有行**的 x 间隙做全局投影推断，而非逐行判断。
   >
   > **强制实现策略（框线优先）：**
   > ① 先做**表格框线检测**（macOS `VNDetectContoursRequest` / 形态学横竖线提取）获取精确单元格边界——真实 Excel 截图、网页表格通常有线，此路径可靠性远高于聚类；
   > ② 仅在检测不到框线时，退化到坐标聚类（y 重叠容差分行 + 全局 x 间隙投影分列 + 合并块按列边界二次切分）；
   > ③ 该滤镜的准确率将成为用户投诉的主要来源，需在 v0.2.0 中配套可视化校正 UI。
2. **【离线极速 OCR】** 截图或扫描件直接提取为纯净可编辑文本。
3. **【二维码与色板提取】** 解析图片内二维码链接及主视觉 Hex/Tailwind 色值。

### 5.4 plainText 通道策略（v1.2 新增，**解决单通道冲突的核心机制**）

> _问题来源（§0.1 I3）：_ `public.utf8-plain-text` 只有**一份**内容，但微信要"美化后的纯文本"、Terminal/VSCode 要"原始 Markdown/代码"。v1.1 把这个矛盾记在 §3.5 的"残留限制"里并给了四条缓解措施，却没有**做决定**——结果是 §10.1 的成功判据（Terminal 拿原文）与 §5 滤镜 1（微信拿精致纯文本）**同时写进了文档，二者不可能同时成立**。

**先排除一个看似优雅的错解（附录 A.10 实测）：**

> ❌ **"那就不接管 plainText 通道，让系统保留原始内容"** —— **实测证明这是陷阱。**
> 只注册 `html` + `rtf` 而不注册 `plainText` 时，AppKit 会**从 RTF 自动合成**纯文本通道，纯文本消费者读到的是 `TRANSFORMED-RTF`，即**转换结果泄漏进了纯文本通道**。
> ✅ 同时实测确认：**显式注册的 provider 优先于 AppKit 合成**。因此 `plainText` 通道**必须始终显式注册并由我们提供值**——这是本策略的实现前提，不是可选项。

**策略枚举（写入 §7.2 `PipeRecipe.output.plainTextPolicy`）：**

| 值 | 语义 | 适用判据 |
|---|---|---|
| `PASSTHROUGH` | plainText 通道输出**用户复制的原始文本**，不做任何加工 | 原始 plainText 本身就是干净、完整、用户想要的东西（Markdown、代码、JSON）|
| `CLEANED` | plainText 通道输出**净化后的文本** | 原始 plainText 本身就是要被清洗的对象（网页垃圾、PDF 硬回车、追踪参数）|
| `SANITIZED_FORCED` | plainText 通道输出**脱敏后的文本**，且**用户不可改、`preserveOriginal` 强制 false** | 命中 `contains_secret`。安全红线，优先级高于一切（原则 4 > 原则 5）|

**内置滤镜的默认映射（v1.2 定案）：**

| 滤镜 | `plainTextPolicy` | 理由 |
|---|---|---|
| 1 AI 星号净化器 | **`PASSTHROUGH`** | 原始 Markdown 就是干净内容；IDE 拿到美化文本 = 代码被改坏（高危），微信拿到原始 Markdown = 少个增强（低危）。**失败代价不对称，选低危侧**|
| 2 网页牛皮癣洗白 | `CLEANED` | 浏览器的文本序列化本身夹带导航/广告垃圾 |
| 3 PDF 断行缝合 | `CLEANED` | 原始态就是断的，缝合是全部价值 |
| 4 社媒链接瘦身 | `CLEANED` | 剥离追踪参数就是滤镜的全部意义 |
| 5 开发者瑞士军刀 | **`PASSTHROUGH`** | 开发者对自动改写容忍度最低 |
| 6 DLP 隐私脱敏盾 | **`SANITIZED_FORCED`** | 安全红线，不可协商 |

**优先级链（运行时按此顺序解析，高者覆盖低者）：**

```
SANITIZED_FORCED（命中 contains_secret，强制）
      ▲ 覆盖
用户在滤镜卡片上的显式选择（§4.4，SANITIZED_FORCED 项锁定不可改）
      ▲ 覆盖
PipeRecipe 自带的 plainTextPolicy 声明
      ▲ 覆盖
角色卡设定的模糊情况默认值（§4.4：💻 → PASSTHROUGH；💼/📊/🎓 → 对 CLEANED 类滤镜给 CLEANED）
      ▲ 覆盖
系统兜底默认 = PASSTHROUGH（原则 5 + 原则 7）
```

> _为什么兜底默认是 `PASSTHROUGH`：_ 未声明策略的第三方社区配方（§11.2 的 `awesome-pasteflow-pipes`）**不应该有能力静默改写用户的纯文本内容**。默认直通意味着社区配方默认只影响 `html`/`rtf` 通道，把破坏面限制在富文本消费者内——这符合原则 7「宁可不接管，不可破坏原生粘贴」的精神。

> _§10.1 成功判据与本节的关系：_ 本策略使 §10.1 的 demo（Word 得到排版富文本 / Terminal 得到原始 Markdown）**默认成立**，无需用户配置。"微信精致纯文本"改为 HUD 手动动作（§5 滤镜 1 修正），不再与之争夺默认值。

### 7.1 剪贴板数据条目 (`ClipboardItem`) — v1.2 修订

```typescript
export interface ClipboardItem {
  id: string;                  // UUID v7 (按时间有序)
  createdAt: number;           // Unix Timestamp (ms)
  contentHash: string;         // BLAKE3 Hash (去重 + 预渲染缓存键 + ⌘C⌘C 双击判定，§3.7)
  primaryType: 'text' | 'html' | 'rtf' | 'image' | 'files';

  /** v1.1 变更：原始内容与各通道产物分离存储，兑现原则 5 */
  original: {
    plainText?: string;
    html?: string;
    rtf?: string;
    imagePath?: string;        // 本地缓存路径
    filePaths?: string[];
  };

  /**

  channels?: {
    html?:      { status: 'pending' | 'ready' | 'failed'; data?: string; pipeId?: string; providedAt?: number };

    plainText?: { status: 'pending' | 'ready' | 'failed'; data?: string; pipeId?: string; providedAt?: number };
  };

  /** v1.2 新增：源格式清单与保全结果（§8.9）。接管前置护栏与直通机制都依赖它 */
  sourceFormats: {
    declaredTypes: string[];      // 接管前源应用声明的全部 pasteboard type（实测可达 12 个）
    itemCount: number;            // pasteboardItems.count；> 1 触发护栏 G2
    passthroughTypes: string[];   // 成功注册直通 provider 的类型
    droppedLegacyTypes: string[]; // 无法直通的 legacy flavor（setDataProvider 静默拒绝）
    preservationComplete: boolean;// 是否完整保全。false ⇒ 依原则 7 放弃接管
  };

  sourceContext: {
    appName: string;           // e.g., "Google Chrome", "Cursor"

    processName: string;       // e.g., "chrome.exe"
    windowTitle?: string;      // e.g., "DeepSeek - 探索未至之境"

     * 容差窗口（建议 500ms），置为 'stale'，此时【不得】用于 matchSourceApps 精确匹配，
     * 只允许匹配通配 '*' 的滤镜。

    resolutionConfidence: 'exact' | 'stale';
  };

  tags: Array<
    | 'markdown' | 'dirty_html' | 'url_with_tracker' | 'pdf_broken_lines'
    | 'json' | 'curl' | 'code' | 'contains_secret' | 'table_image'
  >;

  /**
   * v1.2 新增（§5.4）：本条目最终生效的 plainText 通道策略。
   * 由 §5.4 优先级链解析得出，落库以便诊断面板复现「为什么这条内容被/没被净化」。

  plainTextPolicy: 'PASSTHROUGH' | 'CLEANED' | 'SANITIZED_FORCED';

  isPinned: boolean;
  inStack: boolean;            // 是否处于贪吃蛇收集槽中

  ownership: {
```

### 7.2 声明式滤镜配方协议 (`PipeRecipe`) — v1.2 修订

> _⚠️ v1.2 协议卫生（§0.1 I9）：_ v1.1 的示例 JSON 内夹带了 `v1_1_note`、`matchTargetApps_note`、`minConfidence_note`、`note` 等**编辑期批注字段**。它们语法上是合法 JSON，但这个文件是**机器消费的协议**，而且将被社区当作 `awesome-pasteflow-pipes` 的抄写模板——批注会被当成协议的一部分扩散出去。v1.2 全部移出至下方说明表，并要求 JSON Schema 设 `additionalProperties: false`。

```json
{

  "name": "AI 星号净化器 (Markdown 转办公格式)",
  "description": "将 AI 助手复制的带 # 和 ** 的文本，自动转换为 Word/飞书原生加粗与标准表格",

  "icon": "Sparkles",

  "tier": "L1_LOCAL",

    "matchContentTags": ["markdown"],

```

**字段说明（v1.2 从 JSON 内移出至此）**

| 字段 | 说明 |
|---|---|
| `trigger.ownChannels` | **v1.1 引入，取代 v1.0 的 `matchTargetApps`。** 延迟供给架构下不识别目标应用，改为声明本滤镜愿意供给哪些通道，由消费方的格式请求自然完成分发。<br>⚠️ **v1.2 补充：** 若声明中包含 `html` 或 `rtf`，则 `plainText` **必须同时声明**。实测证明不注册 plainText 时 AppKit 会从 RTF 自动合成该通道，导致转换结果泄漏（§5.4 / 附录 A.10）|
| `trigger.matchTargetApps` | 仅在 §3.6 可选进阶模式（目标应用分支，Tier 1）下生效；**默认架构忽略此字段**，必须为 `null`|
| `trigger.minConfidence` | v1.1 引入。宁可漏判不可错判，避免给普通文本误注入 HTML 导致 Slack / Discord 出现意外富文本。**v1.2 例外：** DLP 类滤镜应设为 `0.5` 左右——漏脱敏的代价远大于误脱敏（§5 滤镜 6）|
| `processor.providerTimeoutMs` | **v1.2 新增。** provider 回调硬超时，默认 `8`。超时即返回原始内容（§8.11）。**上限不得超过 8**；配方声明更大值时运行时按 8 截断，防止社区配方挂死宿主应用|
| `output.channels.*.handler` | 该通道的 L1 handler 名。`html` 需含 `mso-` 样式以保 Word 标题/表格保真度（§8.5）；`plainText` 在 `PASSTHROUGH` 下固定为 `identity`|
| `output.plainTextPolicy` | **v1.2 新增，必填。** 取值 `PASSTHROUGH` / `CLEANED` / `SANITIZED_FORCED`，语义与内置滤镜映射见 **§5.4**。缺省视为 `PASSTHROUGH`（原则 7）|
| `output.preserveOriginal` | v1.1 引入，兑现原则 5。HUD 与抽屉须可取回 `original`。<br>⚠️ **v1.2 强制覆盖：** 命中 `contains_secret` 时运行时**强制置 `false`**，配方里写 `true` 无效（§0.1 I13）|
| `output.toastMessage` | **v1.2 修正时机**：在**接管瞬间**显示，不是粘贴后（§4.1 步骤 4）。文案应描述"将会发生什么"而非"已经发生了什么"，因为我们无法确知粘贴是否真的发生|

> _⚠️ v1.1 修正（保留）：_ v1.0 的 `$schema` 指向 `https://pasteflow.dev/schema/pipe-v1.json`。经核实 **`pasteflow.dev` 尚未注册**，该 URL 当前为死链。**行动项（D6 已决议注册域名）：** 注册后启用该地址；在此之前使用上述 GitHub 托管地址。命名可用性已核实：`pasteflow` 在 **crates.io 与 npm 均未被占用**。

> **v1.2 JSON Schema 强制要求：**
> - `additionalProperties: false` 适用于**所有层级**（根、`trigger`、`processor`、`output`、`output.channels.*`）。这是阻止批注字段与拼写错误字段扩散的唯一有效手段。
> - `plainTextPolicy` 与 `trigger.ownChannels` 为 **required**。
> - `processor.providerTimeoutMs` 加 `maximum: 8`。
> - CI 须对仓库内所有 `pipes/*.json` 跑 schema 校验；社区 PR 同样受此约束。

## 8. 关键技术壁垒与避坑指南 (Critical Edge Cases & Engineering Guardrails)

v1.0 列出 4 项；v1.1 修订其中 3 项、新增 4 项共 7 项；**v1.2 再新增 4 项，共 11 项**。编写 TDD 与实现代码时必须逐项攻克。

> **v1.2 新增的 4 项（§8.8–§8.11）全部源自本轮实测或逻辑推演，且共享同一个失败形态**：用户按 `⌘V`，什么都没发生或发生了错的事，而**我们收不到任何错误信号**。这类静默故障对产品信任的伤害远大于"某次没有自动净化"，因此统一由**原则 7**裁决。

| 节 | 主题 | 来源 | 严重度 |
|---|---|---|---|
| §8.8 | provider 进程退出 → 剪贴板数据蒸发 | **实测复现 + 修法验证通过**（附录 A.8） | 🔴 高（用户退出软件后 `⌘V` 全废）|
| §8.9 | 接管前置护栏与源格式直通 | **实测复现**（附录 A.7 / A.11） | 🔴 高（可能"什么都粘不出来"）|
| §8.10 | Universal Clipboard / Handoff 拉走 provider | 逻辑推演，**待 Step 0 实测** | 🟡 中（隐私语义 + 超时）|
| §8.11 | provider 回调硬超时与降级 | 逻辑推演（基于附录 A.2 实测数据） | 🔴 高（可挂死宿主应用）|

### 8.1 防剪贴板死循环（Loop Guard）— v1.1 修订

- **v1.0 描述的问题：** 软件修改剪贴板写回系统时，会再次触发自身的 Watcher。
- **v1.1 问题形态变化：** 采用延迟供给后，主链路**不再改写剪贴板**，因此经典的"写回自触发"大幅减少。但仍需处理：
    1. provider 被调用时若内部再读写剪贴板，可能触发 changeCount 变化 → 需以 `ownership.changeCountAtOwn` 为基准判定
    2. §3.6 进阶模式与 HUD 注入路径仍会真实写入剪贴板 → 保留 v1.0 方案
- **强制方案：**
    - 每次内部写入前计算 `BLAKE3 Hash` 存入内存环形缓冲区 `RecentInternalWrites`，并附带自定义私有格式标识（`application/x-pasteflow-internal`）。Watcher 检测到标识或匹配 Hash 时短路跳过。
    - 同时维护 `expectedChangeCount`，仅处理非预期的变更。

### 8.2 剪贴板所有权丢失处理（Ownership Loss）— v1.1 新增

- **问题：** 持有式架构下，用户在其他应用复制会调用 `clearContents`（macOS）/ 触发 `WM_CLIPBOARDUPDATE`（Windows），我们的 provider 随之失效。若不处理，会出现"以为还在供给、实际已被顶掉"的静默错误。
- **强制方案：**
    - 持续监听 `NSPasteboard.general.changeCount` / `WM_CLIPBOARDUPDATE`，与 `ownership.changeCountAtOwn` 比对。
    - 检测到所有权丢失 → 标记 `ownership.owned = false`、记录 `lostAt`、清理 provider 强引用（避免泄漏）、停止一切供给。
    - **不得尝试夺回剪贴板**（会与其他剪贴板管理器打架，见 §8.6）。

### 8.3 跨软件粘贴格式兼容性（Clipboard MIME Negotiation）— v1.2 强化

- **问题：** 往 Word 贴表格和往微信贴文字所需的底层格式截然不同。
- **强制方案：** 声明并供给全部通道——`CF_HTML` / `public.html`、`CF_RTF` / `public.rtf`、以及按 §5.4 策略决定的 `CF_UNICODETEXT` / `public.utf8-plain-text`。支持富文本的目标（Word/飞书）自动读 HTML/RTF，仅支持纯文本的目标（微信/记事本）读 plainText 通道。
- **v1.1 强化：** 此机制现已由**架构本身**保证（§3.2 格式协商），不再依赖运行期判断目标应用。但**"生成了 HTML"≠"Word 里好看"**，见 §8.5。

- **⚠️ v1.2 新增：通道声明三铁律（均由本机实测确立，附录 A.10 / A.11）**

  **R1 — `plainText` 通道必须显式注册，不得省略。**
  实测：只注册 `html` + `rtf` 时，AppKit 会**从 RTF 自动合成**纯文本通道，纯文本消费者读到的是 `TRANSFORMED-RTF`——转换结果**泄漏**进纯文本通道，Terminal 与微信都会拿到被改写的文本。
  ⇒ "不接管 plainText 以保留原始内容"是一个**看似优雅实则错误**的方案，必须显式提供我们自己的值。

  **R2 — 显式注册的 provider 优先于 AppKit 合成。**
  实测：同时注册 `plainText` / `html` / `rtf` 三个 provider 后，纯文本消费者读到的**正是**我们 provider 返回的值，未被 RTF 派生结果覆盖。
  ⇒ 这是 §5.4 `plainTextPolicy` 能够生效的实现前提。

  **R3 — legacy 别名由 AppKit 自动合成，不需要也无法为其注册 provider。**
  `setDataProvider(forTypes:)` 对 legacy 标识符**静默拒绝**（仅打印 `is not a valid UTI string` 警告，不抛错）。实测合成映射：

  | 注册的现代 UTI | AppKit 自动追加的别名（实测，**不含该 UTI 自身**） |
  |---|---|
  | `public.utf8-plain-text` | `NSStringPboardType` |
  | `public.html` | `Apple HTML pasteboard type` |
  | `public.rtf` | `NeXT Rich Text Format v1.0 pasteboard type`、`public.utf16-external-plain-text`、`CorePasteboardFlavorType 0x75743136`、`public.utf8-plain-text`、`NSStringPboardType` |
  | `public.file-url` | `CorePasteboardFlavorType 0x6675726C`、`NSFilenamesPboardType`、`Apple URL pasteboard type` + 2 个 dynamic UTI |
  | `public.url` | `CorePasteboardFlavorType 0x75726C20`、`Apple URL pasteboard type` + 1 个 dynamic UTI |
  | `public.png` | `Apple PNG pasteboard type`、`public.tiff`、`NeXT TIFF v4.0 pasteboard type` |
  | `public.text` | _（无）_ |

  ⇒ 两条推论：① 直通源格式时**只需注册现代 UTI**，legacy 别名会自动出现；② `public.rtf` 会连带合成 `public.utf8-plain-text`——这**再次印证 R1**：若不显式注册 plainText，RTF 会替我们决定纯文本通道的内容。

  > _⚠️ 注意：_ AppKit 会**声明**它无法真正供给的合成别名。实测 `public.utf16-external-plain-text` 出现在 `types` 中，但读取返回 `nil` 且 provider 未被调用。消费方若只认这个类型会拿到空值——**这不是我们的 bug，但需在 §8.5 兼容性矩阵中记录哪些应用会踩到**。

### 8.4 输入光标坐标获取与回退机制（Caret Position Fallback）— 保留

- **问题：** 原生 Win32 应用 / Electron 应用 / 浏览器 Canvas 中，Accessibility API 不一定能拿到 caret 的精确屏幕坐标。
- **强制方案（三级回退）：**
    1. `UIAutomation`（Win）/ `AXUIElement`（Mac）获取精确 caret 坐标
    2. 失败 → 回退至鼠标指针坐标偏移 `(12px, 12px)`
    3. 鼠标在屏幕外 → 回退至活动窗口正中偏下
- **v1.1 补充：** 此能力需 Accessibility（macOS）/ UIA（Windows）权限，**不属于零权限核心链路**，仅在 HUD 手动挡中使用。权限缺失时直接走第 2 级回退，不得阻塞或反复弹窗索要权限。

### 8.6 与其他剪贴板管理器共存（Coexistence）— v1.1 新增

- **问题：** 用户可能同时运行 Ditto / Maccy / CopyQ / EcoPaste / PowerToys / Windows Win+V 历史。两个组件同时争夺剪贴板所有权会导致内容丢失、互相触发死循环、以及"我的转换莫名失效"。
- **强制方案：**
    - 启动时探测常见剪贴板管理器的运行状态（进程名匹配），若检测到则**主动提示用户存在冲突风险**并建议二选一，而非静默竞争。
    - 严格遵守 §8.2：所有权被夺走时**不尝试夺回**。
    - 在 Windows 上写入时附带 `ExcludeClipboardContentFromMonitorProcessing` / `CanIncludeInClipboardHistory = 0`，避免污染 Win+V 历史（对 DLP 标记为敏感的条目**强制**如此）。
    - 提供诊断面板显示当前剪贴板所有者与 changeCount 时间线，便于用户自查（§11.4）。

### 8.7 隐私安全绝对红线（Security Blacklist）— 保留（已核实准确）

- **强制方案：** 内置**不可关闭**的敏感源过滤。当复制源进程为 `1Password`、`Bitwarden`、`KeePass`、`KeePassXC`、`Keychain Access`，或内容携带系统级隐私标记时，**完全忽略该次复制：不进内存、不落盘、不触发任何管道、不接管剪贴板所有权**。
- **v1.1 核实结果：✅ v1.0 此节技术描述准确，机制均真实存在：**
    - macOS：`org.nspasteboard.ConcealedType`（真实约定，KeePassXC 等在用）
    - Windows：`ExcludeClipboardContentFromMonitorProcessing`（MS 官方文档确认：置入任意数据即可阻止所有格式进入剪贴板历史或同步到其他设备）
    - 相关格式另有 `CanIncludeInClipboardHistory`、`CanUploadToCloudClipboard`（序列化 DWORD，0 = 阻止，1 = 显式请求），以及较早的 `Clipboard Viewer Ignore`
    - 均需通过 `RegisterClipboardFormat` 取得标识值
- **v1.1 补充要求：** 敏感条目**不得**进入 L3 AI 链路，即使用户显式选择 AI 滤镜也须二次确认并本地脱敏。

- **⚠️ v1.2 补充要求（§0.1 I13，**不可协商**）：** v1.1 本节只覆盖了"复制**源**是密码管理器"的情形，**没有覆盖"普通应用复制出的内容里夹带密钥"**（如从 `.env` 文件、CI 日志、Slack 消息里复制）。后者由 §5 滤镜 6（DLP 脱敏盾）处理，而 v1.1 的两处设计会让 DLP 形同虚设：
    - §4.2 要求 HUD "**始终**包含「粘贴原始内容」"
    - §7.2 配方默认 `preserveOriginal: true`

  持有式架构把这个洞**放大了**：v1.0 原地重写后明文物理上就消失了；v1.2 主动把明文保存在进程内并承诺一键可取回。DLP 滤镜若只改通道而保留回贴入口，等于没做。

  **强制规则（优先级高于原则 5）：** 命中 `contains_secret` 的条目——
    1. `html` / `rtf` / `plainText` **三个通道全部输出脱敏结果**，无一例外；
    2. `plainTextPolicy` 强制为 `SANITIZED_FORCED`，用户不可改（§5.4）；
    3. `preserveOriginal` 运行时**强制置 `false`**，配方声明无效；
    4. HUD 与抽屉的「粘贴原始内容」**置灰**并显示原因 `🔒 含敏感信息，原文回贴已禁用`；
    5. 原始明文可留存于本地 SQLite 供用户自查（原则 4 的本地优先），但**不存在任何把它写回剪贴板的路径**；
    6. Windows 侧写入时强制附带 `ExcludeClipboardContentFromMonitorProcessing` 与 `CanIncludeInClipboardHistory = 0`，避免进入 Win+V 历史与云同步（§8.6）；
    7. **macOS 侧须阻止 Handoff 外泄**（§8.10）——延迟供给下 `sharingd` 拉取的是我们的 provider，若不处理，脱敏前的内容语义仍可能流向其他设备。

### 8.8 provider 进程退出导致数据蒸发（Eager Materialization）— v1.2 新增

- **问题（🔴 已实测复现，附录 A.8）：** 延迟供给的数据**活在本进程的内存里**。owner 进程退出后：

  ```
  OWNER:  已接管剪贴板, changeCount=31, 声明类型=["public.utf8-plain-text", "NSStringPboardType"]
  OWNER:  进程即将退出（模拟用户退出 PasteFlow / 崩溃）
  READER: changeCount=31, 声明类型=[]
  READER: 读到内容 = ❌ nil（数据已随 owner 进程消亡）
  ```

  危险之处在于**它看起来完全正常**：`changeCount` 没有变化，其他剪贴板管理器看到的历史条目还在，用户也记得自己刚复制过东西——但 `⌘V` **什么都粘不出来**。触发场景包括：用户主动退出 PasteFlow、应用崩溃、系统内存压力杀进程、以及**用户在复制后立刻退出软件再去别处粘贴**（这是最常见的路径）。

  > _v1.0 没有这个问题：_ 急切重写把真实数据写进了系统剪贴板，进程退出后数据仍在。这是持有式延迟供给**架构独有**的代价，v1.1 完全未识别。

- **强制方案（已实测验证通过，附录 A.8）：**
    1. **宽限期物化：** 接管后启动定时器（建议 **1s**），到期把所有已声明通道**急切物化**——即调用一次全部 L1 handler，把结果作为真实数据重新写入剪贴板，此后不再依赖本进程。
    2. **退出前无条件物化：** 在 `applicationWillTerminate`（macOS）/ `WM_QUERYENDSESSION` + `WM_ENDSESSION`（Windows）中再执行一次，覆盖"用户在宽限期内就退出"的情形。
    3. **⚠️ 物化前必须校验所有权：** 仅当 `NSPasteboard.general.changeCount == ownership.changeCountAtOwn` 时才物化。**否则会顶掉用户在宽限期内复制的新内容**——这是本方案自身引入的新竞态（§3.4 收益 4）。
    4. **物化会被 Loop Guard 看到：** 实测物化使 `changeCount` +1（32→33）。必须把该次写入登记进 §8.1 的 `RecentInternalWrites`，否则自己的 watcher 会把它当成"用户又复制了一次"。
    5. **物化后更新 `ownership.materializedAt` 与 `materializeChangeCount`**，供诊断面板（§11.4）复现时序。

- **宽限期取值的权衡：**
    | 宽限期 | 优点 | 缺点 |
    |---|---|---|
    | 0（立即物化） | 最安全，无蒸发窗口 | 完全丧失延迟供给优势，退化为 v1.0 的急切重写 |
    | **1s（建议）** | 覆盖绝大多数"复制后立刻切窗口粘贴"（实测人手切换 + `⌘V` 通常 >1s），且退出蒸发的暴露窗口很短 | 1s 内退出仍有小概率蒸发 |
    | 5s+ | 延迟供给优势最大 | 蒸发窗口过长，不可接受 |

    ⇒ **建议 1s，并在 Step 0 spike 中用真实操作节奏校准**（§12）。

- **降级路径：** 若物化本身失败（例如 handler panic），**不得**留下半物化状态。应放弃所有权、清理 provider 引用，让剪贴板回到系统原生行为（原则 7）。

### 8.9 接管前置护栏与源格式直通（Ownership Guards）— v1.2 新增

- **问题（🔴 已实测复现，附录 A.7 / A.11）：** 接管动作必须调用 `clearContents()`，实测使源应用声明的 **12 个 type 全部归零**：

  ```
  接管前: 12 个 type（含 org.chromium.source-url、Excel 私有 UTI、ConcealedType 等）
  clearContents() 后: 0 个 type，私有 UTI 已被抹杀
  ```

  直通机制（枚举源 type → 缓存其 `Data` → 用 provider 逐个重新声明 → 只覆盖要改的通道）**对合法 UTI 有效**：实测 12 个 type 全部还原，`.html` 成功覆盖。
  **但对 legacy 4 字符 flavor 无效**：`setDataProvider` 静默拒绝，实测结果为 `接管后 types = []`、**数据完全不可读**。这比不接管更糟——用户的 `⌘V` 会彻底失败。

- **强制方案 A：直通机制**
    1. 接管前枚举 `pasteboard.types`（macOS）/ `EnumFormatEtc`（Windows），把每个类型的 `Data` 读入内存缓存；
    2. 用**一个** provider 为全部可注册类型重新声明；
    3. 需要转换的通道由对应 handler 覆盖，其余类型原样返回缓存数据；
    4. 结果记入 §7.1 的 `sourceFormats`（`passthroughTypes` / `droppedLegacyTypes` / `preservationComplete`）。

- **⚠️ 强制方案 B：UTI 合法性过滤——用错判据会静默丢数据**

  实测证明**`UTType(s) != nil` 是错误的过滤判据**：

  | 标识符 | `UTType()` 结果 | `setDataProvider` 能否注册 |
  |---|---|---|
  | `public.utf8-plain-text` / `public.html` / `public.rtf` | ✅ 非 nil | ✅ 能 |
  | `org.chromium.source-url` | ❌ **nil** | ✅ **能** |
  | `com.microsoft.excel.data` | ❌ **nil** | ✅ **能** |
  | `org.nspasteboard.ConcealedType` | ❌ **nil** | ✅ **能** |
  | `dyn.ah62d4rv4ge80e2pw` | ✅ 非 nil（dynamic） | ✅ 能 |
  | `NSStringPboardType` / `Apple HTML pasteboard type` / `NSFilenamesPboardType` / `Apple URL pasteboard type` / `CorePasteboardFlavorType 0x6675726C` | ❌ nil | ❌ **不能** |

  ⇒ 未注册的第三方反向 DNS 标识符（Chrome、Excel）虽然 `UTType()` 返回 nil，**却是完全可注册的合法 pasteboard type**。用 `UTType()` 过滤会把它们全部丢掉，且**没有任何报错**。

  **正确判据：只排除已知 legacy 别名集合**，正则：

  ```
  ^(NS\w+PboardType|Apple .+ pasteboard type|NeXT .+ pasteboard type|CorePasteboardFlavorType 0x[0-9A-Fa-f]{8})$
  ```

  排除它们的理由是安全的：由 §8.3 R3，这些别名会由 AppKit 从对应现代 UTI **自动合成**回来。

- **强制方案 C：接管前置护栏 G1–G4（依原则 7，任一不通过即放弃接管）**

  | # | 条件 | 理由 | 实测依据 |
  |---|---|---|---|
  | **G1** | 源 types 中存在 legacy flavor，且其**对应现代 UTI 不在**源 types 中 | 该 legacy 数据既无法直通、AppKit 也不会合成 → 接管后必然丢失 | 附录 A.7 |
  | **G2** | `pasteboardItems.count > 1` | 单 item 接管会把结构压平。实测：复制 2 个文件后 `count=2`，单 item 接管后**塌成 1** | 附录 A.11 |
  | **G3** | 源 types 含 `public.file-url` / `NSFilenamesPboardType` | 文件复制没有转换语义，且 legacy flavor 密集（实测 6 个 type 中 4 个是 legacy/dynamic）| 附录 A.11 |
  | **G4** | 直通后 `preservationComplete == false` | 兜底闸。任何无法完整保全源格式的情形一律放弃 | 附录 A.7 |

  **legacy → 现代 UTI 对应表（G1 判定用）**

  | legacy 标识符 | 对应现代 UTI |
  |---|---|
  | `NSStringPboardType` | `public.utf8-plain-text` / `public.text` |
  | `Apple HTML pasteboard type` | `public.html` |
  | `NSFilenamesPboardType` | `public.file-url` |
  | `Apple URL pasteboard type` | `public.url` / `public.file-url` |
  | `NeXT Rich Text Format v1.0 pasteboard type` | `public.rtf` |
  | `NeXT TIFF v4.0 pasteboard type` | `public.tiff` |
  | `Apple PNG pasteboard type` | `public.png` |
  | `CorePasteboardFlavorType 0x6675726C`（`furl`）| `public.file-url` |
  | `CorePasteboardFlavorType 0x75726C20`（`url `）| `public.url` |
  | `CorePasteboardFlavorType 0x75743136`（`ut16`）| `public.utf16-external-plain-text` |

- **可观测性要求：** 每次因护栏放弃接管都必须在诊断面板（§11.4）留下记录，含护栏编号与源 types 清单。**这是判断"自动挡为什么没生效"的唯一线索**——放弃接管对用户是完全静默的。

### 8.10 Universal Clipboard / Handoff 交互 — v1.2 新增

- **问题（🟡 逻辑推演，待 Step 0 实测）：** macOS 的 `sharingd` 会代表 Handoff / Universal Clipboard 读取剪贴板，以便在用户的 iPhone / iPad / 其他 Mac 上提供"来自 Mac 的剪贴板"。在持有式架构下它会**拉取我们的 provider**，带来两个后果：
    1. **隐私语义：** 转换结果（可能含 `CLEANED` 但未达 `contains_secret` 阈值的内容）会被同步到用户的其他 Apple 设备。这在 v1.0 的急切重写架构下同样存在，但延迟供给让"谁读了我们的数据"变得不可见——provider 回调不携带调用方身份（附录 A.9），我们**无法区分 Word 与 `sharingd`**。
    2. **超时风险：** `sharingd` 对 provider 回调的等待容忍度未知。L1 在 8ms 内必然来得及；但一旦触发 L2 冷启动（13.5s）就是超时——这正是 §8.11 硬超时存在的另一个理由。

- **强制方案：**
    - **列入 Step 0 spike 必测项**（§12）：在开启 Handoff 的机器上，观察 provider 是否被 `sharingd` 调用、调用时机、以及超时行为。
    - **首次接管时明确告知**用户"转换结果可能经由 Universal Clipboard 同步至你的其他 Apple 设备"（原则 4 的告知义务），并在设置中提供关闭方式。
    - **`contains_secret` 条目必须阻止外泄**（§8.7 第 7 条）。macOS 无 Windows 那样的 `CanUploadToCloudClipboard` 等价标记，可行手段是：对敏感条目**不接管**（保持系统原生行为，由源应用的隐私标记自行决定），或接管后在物化时写入 `org.nspasteboard.ConcealedType`。
      > _⚠️ 未验证：_ 由 PasteFlow 后置写入 `ConcealedType` 是否真能阻止 `sharingd` 同步，**须实测**。若不能，则对敏感条目一律走"不接管"路径。
    - 诊断面板记录 provider 调用次数与时间戳，帮助识别异常的第三方拉取方。

### 8.11 provider 回调的硬超时与降级（Callback Budget）— v1.2 新增

- **问题（🔴 本版最高危修正，§0.1 I4）：** provider 回调运行在**宿主应用的粘贴请求上下文**中。回调耗时多久，用户的 `⌘V` 就卡多久。v1.1 在数据流图里把 `[L2 Engine 热态 <100ms]` 画进了回调内部，而 L2 的**机器级首次调用实测 13,554ms**（附录 A.2）。在回调里同步跑 OCR 等于挂死 Word，而且**我方收不到任何错误信号**，用户只会看到应用转圈。

- **强制方案：**
    1. **回调内只允许 L1。** L2 / L3 一律走 Path D 后台预热或 HUD 手动触发（§6.4）。
    2. **8ms 硬超时。** 实现方式：把 handler 调用放在可取消的执行单元中，超时即放弃并返回原始内容。**不得**依赖"handler 自己会很快"这种假设——正则回溯灾难（catastrophic backtracking）在真实脏 HTML 上是会发生的。
    3. **超时 / panic / 任何异常 → 返回原始内容**，绝不返回空数据、绝不阻塞。返回空数据会让宿主应用判定"剪贴板没有我要的格式"，进而可能回退到别的行为或直接失败（原则 7）。
    4. **handler 内严禁任何 I/O**：磁盘、网络、SQLite 写入。缓存查询只允许命中内存态。落库走异步回写（§4.3）。
    5. **配方层的 `providerTimeoutMs` 上限为 8**（§7.2），运行时截断更大的声明值，防止社区配方挂死宿主应用。
    6. **正则安全：** 所有 L1 handler 使用的正则必须经 `regex` crate 的线性时间保证（Rust `regex` 不使用回溯，天然免疫灾难性回溯）。**禁止**引入任何带回溯的正则引擎（如 `fancy-regex` 的回溯模式）到 provider 路径中。

- **验收测试（须进 CI）：** 构造 1MB 脏 HTML、深层嵌套 JSON、超长单行文本三类病态语料，断言 provider 回调 p99 `< 8ms` 且**永不返回空**。

  **配套动作：** 每个源文件加 SPDX 头（`SPDX-License-Identifier: Apache-2.0`）；`NOTICE` 文件列出 `clipboard-rs` 等依赖的许可；社区配方仓库 `awesome-pasteflow-pipes` 单独采用 **CC0**，避免配方 JSON 被许可条款拖累传播。
- **Mac App Store：暂不可行。** 两个独立障碍：① 启用 Tier 1 或 §3.6 进阶模式需 Accessibility，MAS 应用无法获得该权限；② **即便只发布 Tier 0 构建，MAS 沙盒是否允许长时间持有 `NSPasteboard` 所有权尚未验证**——延迟供给要求我方进程持续作为 pasteboard 的 data provider，这与沙盒的生命周期约束可能冲突。
  > _⚠️ v1.2 措辞收敛：_ §3.7 提到"MAS 上架可行性仅限 Tier 0 构建"，**这是待验证的可能性，不是已确认的结论**。在障碍 ② 被实测澄清前，**不得对外宣称"可上架 MAS"**。
  **主分发渠道为 GitHub Releases + 自建下载页 + Homebrew Cask**。
- **自动更新：** Tauri updater（需自建或托管 update manifest）。
- **Windows 分发：** 考虑 Microsoft Store（可规避 SmartScreen）与 `winget` 提交。

### 11.4 可观测性（本地优先前提下）— v1.2 扩充

- **问题：** 原则 4 要求本地优先、不做行为追踪。但 §8.1 指出钩子会被系统**静默卸载且应用无法感知**，§8.2 的所有权丢失同样是静默的。**没有可观测性，我们无法知道自动挡是否还在工作，用户只会觉得"这软件时灵时不灵"。**
  > _⚠️ v1.2 加重（§0.1 I10 / I11 / I4）：_ 持有式架构引入的**三类新故障全部是静默的**，可观测性从"锦上添花"变成了"没有它就无法定位任何线上问题"：
  > - **护栏放弃接管**（§8.9 G1–G4）：用户看到的是"这次 `⌘C` 软件没反应"，与"软件崩了"在体感上完全相同；
  > - **provider 回调超时降级**（§8.11）：用户看到的是"粘出来的是原始 Markdown，滤镜没生效"，**且我方收不到任何错误信号**——回调运行在宿主进程上下文；
  > - **急切物化未发生**（§8.8）：用户看到的是"退出软件后剪贴板空了"，且往往在几分钟后的另一次粘贴里才暴露，与因果点相距甚远。
- **强制方案：**
    1. **本地诊断面板**（默认提供，无需联网）：显示当前剪贴板所有者、`changeCount` 时间线、钩子健康状态与最近重装记录、各滤镜近 7 天触发次数、provider 调用成功率与耗时分位数。
        > _v1.2 新增面板字段（与 §7.1 数据结构一一对应）：_
        > - **护栏放弃记录**：时间戳 + 触发的护栏 ID（G1/G2/G3/G4）+ 源声明的 `types` 清单 + `droppedLegacyTypes`。这是回答"为什么这次没转换"的**唯一**依据。
        > - **provider 回调耗时分位数**：p50 / p95 / **p99**，以及**超时降级次数**（§8.11 要求 p99 < 8ms 进 CI）。
        > - **物化时序**：`materialized` / `materializedAt` / `materializeChangeCount`，以及"因所有权已丢失而放弃物化"的计数（§8.8 第 3 条）。
        > - **`resolutionConfidence: 'stale'` 计数**（§4.1 步骤 1 / §7.1）：SourceApp 解析退化到环形缓冲兜底的比例。**该比例升高即意味着用户在快速切窗，滤镜误匹配风险上升**，是决定是否要改判定窗口的关键指标。
        > - **原文回贴禁用条目数**（`originalReplayDisabled`，§0.1 I13）：让用户看见 DLP 实际拦截了多少次，把"不可关闭的红线"变成可感知的保护。
    2. **本地结构化日志**（滚动、可一键导出），用于用户提 issue 时附带。
        > _v1.2 强制脱敏规则：_ 日志中**只允许**出现内容的 `contentHash`（BLAKE3）与长度，**严禁**出现剪贴板原文或任何转换产物。护栏记录里的 `types` 清单是 UTI 字符串（非内容），可以记录。
    3. **可选的匿名错误上报**：默认**关闭**，首次开启时明确列出将上传的字段清单，且**绝不包含剪贴板内容**（仅错误码、OS 版本、滤镜 id、耗时分位数）。
        > _v1.2 补充白名单字段：_ 护栏 ID、超时降级计数、`stale` 解析计数。**仍然不含**任何 type 名称以外的源应用信息，不含 bundleId。
    4. **§8.5 兼容性矩阵的 CI 结果**公开发布在每次 release notes 中——既是质量保证，也是差异化传播素材。
    5. **（v1.2 新增）Step 0 spike 的 B1–B11 验证结果**同样公开在首个 release notes 中。这批验证项覆盖了持有式架构的全部静默故障面（§12），公开它们比公开功能列表更能建立 HN 受众要的"可审计性"信任（§11.5 第二波策略）。

## 附录 A：实测数据记录 (Verified Benchmarks)

> 以下数据均于 **2026-10-14** 在 **macOS 27.0.1 (Build 26A434)** 上实测得出，非文档推断。第三方数据已标注来源。固化于此以便后续复现与回归对比。

### A.1 持有式延迟供给（`NSPasteboardItemDataProvider`）— ✅ 验证通过

**测试方法：** 创建 `NSPasteboardItem`，通过 `setDataProvider(_:forTypes:)` 声明 `.string` 与 `.html` 两通道但**不写入任何数据**；`clearContents()` + `writeObjects()` 后分别以纯文本消费方与富文本消费方身份读取。

**实测输出：**

```
writeObjects 成功: true
写入后 provider 调用次数: 0        ← 数据未生成，延迟供给生效
已声明类型: [public.utf8-plain-text, NSStringPboardType, public.html, Apple HTML pasteboard type]

[纯文本消费方] 读到: 纯文本通道内容
  → provider 调用记录: ["public.utf8-plain-text"]
[富文本消费方] 读到: <h2>标题</h2><p>正文<b>加粗</b></p>
  → provider 调用记录: ["public.utf8-plain-text", "public.html"]
```

**结论：** ① 写入后 provider 调用 0 次，证明数据确实延迟生成；② 剪贴板在写入时即**声明**了两个通道，消费方能看到可用性；③ 每个消费方**只触发自己所需通道**的回调；④ 全程未发生任何"重写"，原始数据始终由本进程持有。
**⇒ v1.1 §3 架构成立。**

**实现注意：** provider 对象必须**强引用保活**，否则回调无法送达。

**对照组（多格式同时写入）：** 另测 `setString(html, forType: .html)` + `setString(plain, forType: .string)` 急切写入方式，同样成功且两通道可独立读回（声明类型 `[public.html, Apple HTML pasteboard type, public.utf8-plain-text, NSStringPboardType]`）。**该方式实现更简单但不具备延迟供给与非破坏性优势**，可作为 spike 阶段的降级备选。

### A.8 provider 进程退出导致数据蒸发 + 急切物化修法 — 🔴 复现并验证

**测试目的：** 验证一个 v1.1 与本轮审查**都未识别**的风险——延迟供给的数据活在本进程内存中，owner 进程退出后是否还读得到。

**测试方法：** 两个独立进程。`owner` 接管剪贴板（lazy provider）→ 打印状态 → 退出；`reader` 在 owner 退出后读取。

**实测输出（未物化）：**

```
OWNER:  已接管剪贴板, changeCount=31, 声明类型=["public.utf8-plain-text", "NSStringPboardType"]
OWNER:  进程即将退出（模拟用户退出 PasteFlow / 崩溃）
READER: changeCount=31, 声明类型=[]
READER: 读到内容 = ❌ nil（数据已随 owner 进程消亡）
```

**⚠️ 注意失败形态的隐蔽性：** `changeCount` **没有变化**（仍是 31），其他剪贴板管理器看到的历史条目仍在，用户也记得自己刚复制过——但 `⌘V` 什么都粘不出来，且**我方进程已死，不可能收到任何错误信号**。

**修法验证（急切物化）：** 接管 → 宽限期到期 → 把所有声明通道写为真实数据 → 退出：

```
=== 阶段 1：延迟供给接管 ===
接管后 changeCount=32, types=["public.utf8-plain-text", "NSStringPboardType", "public.html", "Apple HTML pasteboard type"]

=== 阶段 2：宽限期到期，急切物化 ===
物化后 changeCount=33, types=["public.utf8-plain-text", "NSStringPboardType", "public.html", "Apple HTML pasteboard type"]
物化后本进程自读 plainText=LAZY-PROVIDED-TEXT

=== 阶段 3：owner 进程退出 ===
=== READER（独立进程，owner 已退出）===
owner 记录的 changeCount: lazy=32, eager=33
当前 changeCount=33
当前声明 types=["public.utf8-plain-text", "NSStringPboardType", "public.html", "Apple HTML pasteboard type"]
读到 plainText = LAZY-PROVIDED-TEXT      ✅
读到 html      = <p>LAZY-PROVIDED-HTML</p> ✅
pasteboardItems.count = 1
```

**结论：**

- 🔴 **风险真实存在且严重**：用户"复制 → 退出 PasteFlow → 到别处粘贴"是最常见的路径之一。
- ✅ **急切物化修法有效**，数据脱离 owner 进程存活。
- ⚠️ **副作用 1：物化使 `changeCount` +1**（32→33）。必须登记进 §8.1 的 `RecentInternalWrites`，否则自己的 watcher 会误判为新复制。
- ⚠️ **副作用 2：物化是一次真实写入，会顶掉期间的新复制。** 必须先校验 `changeCount == changeCountAtOwn`（§8.8 第 3 条）。
- ⇒ **v1.2 §8.8 由此产生。** 该节同时说明：这是持有式延迟供给**架构独有**的代价，v1.0 的急切重写反而没有此问题。

### A.9 provider 回调的调用方身份 + `⌘C⌘C` 零权限检测可行性

**测试目的：** ① 确认能否在 provider 回调中识别请求方（决定 Ghost Toast 能否靠启发式过滤解决）；② 确认 `⌘C⌘C` 双击检测能否绕开 event tap（决定 Tier 0 能否真正零权限）。

**实测结论 ①：`pasteboard(_:item:provideDataForType:)` 的签名中不含任何调用方身份信息。**

```swift
func pasteboard(_ pb: NSPasteboard?,
                item: NSPasteboardItem,
                provideDataForType type: NSPasteboard.PasteboardType)
//  可获得的只有：pasteboard 本身、item、被请求的 type
//  ❌ 无 PID、无 bundleId、无进程名
```

⇒ **无法区分** Word 的真实粘贴、Finder 快速查看的预读、Alfred 的扫描、以及 Handoff `sharingd` 的同步拉取。
⇒ 本轮审查提出的缓解措施「若同一进程短时间内遍历请求多个通道则不出 Toast」**在 macOS 上不可实现**——"同一进程"这个前提无法判定。
⇒ **v1.2 §4.1 步骤 4 改为在接管时出 Toast**，从构造上消灭幽灵态。

**实测结论 ②：`changeCount` 对内容相同的重复复制依然自增。**

```
第 1 次 ⌘C：changeCount = 28
第 2 次 ⌘C：changeCount = 29   （间隔 0.18ms，内容与第 1 次完全相同）
第 3 次 ⌘C：changeCount = 30   （间隔 0.18ms，内容与第 2 次完全相同）
```

⇒ **`⌘C⌘C` 可以完全不依赖 CGEventTap 检测**，从而不需要 Input Monitoring 权限。
⇒ **v1.2 §3.7 的 Tier 0 由此成立。** 判定需三条件同时满足（250ms 内 ≥2 次自增 + 同 `contentHash` + 同 `SourceApp`），以防"两个应用间快速复制不同内容"与"源应用两阶段写入"造成误触发。

> _⚠️ 实现注意（v1.2 新发现）：_ 若第一次 `⌘C` 已被我方接管，第二次 `⌘C` 会让源应用调用 `clearContents` → `changeCount` 前进 → **§8.2 会判定为所有权丢失**。因此 `DoubleCopyDetector` 必须挂在所有权状态机**之前**，或让状态机识别"新内容与当前持有内容同 hash"这一特例，否则第二次复制会被当成普通顶替处理，**双击永远触发不了**。

> _📌 关于审查中"Maccy / PopClip 均用此技巧"的说法：_ `changeCount` 机制本身已由本测试验证为真，但**这两个项目是否确实如此实现未经查证**，属转述性断言。v1.2 正文**不引用**该说法，只引用本机实测数据。

### A.10 通道优先级：显式 provider vs AppKit 自动合成 — 🔴 决定性测试

**测试目的：** 解决 §3.5 的"单通道冲突"。一个看似优雅的方案是"只接管 `html`/`rtf`，不接管 `plainText`，让系统保留原始纯文本"。本测试验证该方案是否成立。

**实测输出：**

```
【场景 1】显式注册 plainText + html + rtf 三个 provider
声明 types = [public.utf8-plain-text, NSStringPboardType, public.html,
              Apple HTML pasteboard type, public.rtf,
              NeXT Rich Text Format v1.0 pasteboard type,
              public.utf16-external-plain-text, CorePasteboardFlavorType 0x75743136]

  纯文本消费者读 public.utf8-plain-text
    → "RAW-MARKDOWN **bold** # h1"
    ✅ 拿到我们 provider 的原始直通值，未被 RTF 合成覆盖
  富文本消费者读 public.rtf
    → 含 "TRANSFORMED-RTF" = true  ✅
  读 AppKit 自动合成的 public.utf16-external-plain-text
    → nil  ⚠️ 被声明但无法供给，provider 未被调用
  provider 实际被调用的通道 = ["public.utf8-plain-text", "public.rtf"]

【场景 2 · 对照组】只注册 html + rtf，【不】注册 plainText
声明 types = [public.html, Apple HTML pasteboard type, public.rtf,
              NeXT Rich Text Format v1.0 pasteboard type,
              public.utf16-external-plain-text, CorePasteboardFlavorType 0x75743136,
              public.utf8-plain-text, NSStringPboardType]     ← ⚠️ plainText 自己出现了
  纯文本消费者读到 = "TRANSFORMED-RTF"      🔴 转换结果泄漏进纯文本通道
  provider 被调用 = ["public.rtf"]           ← AppKit 拿 RTF 合成了纯文本
```

**结论（三条，全部写入 §8.3）：**

1. 🔴 **"不接管 plainText 通道以保留原始内容"是陷阱。** AppKit 会从 RTF **自动合成**纯文本通道，消费者拿到的是**转换结果**。若按此实现，Terminal 与微信都会收到被改写的文本，而我们的代码里根本没有任何一行碰过 plainText——**极难排查**。
2. ✅ **显式注册的 provider 优先于 AppKit 合成。** 这是 §5.4 `plainTextPolicy` 能够生效的实现前提。
3. ⚠️ **AppKit 会声明它无法供给的合成别名。** `public.utf16-external-plain-text` 出现在 `types` 中却读回 `nil`，provider 也未被调用。消费方若只认这个类型会拿到空值。需在 §8.5 兼容性矩阵中记录哪些应用会踩到。

⇒ **`plainText` 通道必须始终显式注册并由我们提供值。这不是可选项。**

| `org.nspasteboard.ConcealedType` | ❌ **nil** | ✅ **可注册** |
| `NSStringPboardType` | ❌ nil | ❌ **静默拒绝** |
| `Apple HTML pasteboard type` | ❌ nil | ❌ **静默拒绝** |
| `NSFilenamesPboardType` | ❌ nil | ❌ **静默拒绝** |
| `Apple URL pasteboard type` | ❌ nil | ❌ **静默拒绝** |
| `CorePasteboardFlavorType 0x6675726C` | ❌ nil | ❌ **静默拒绝** |

**🔴 关键结论：`UTType(s) != nil` 是错误的过滤判据。**

未向 LaunchServices 注册的第三方反向 DNS 标识符（Chrome 的 source-url、Excel 的私有数据、乃至隐私标记 `ConcealedType`）都返回 nil，**却是完全可注册的合法 pasteboard type**。用 `UTType()` 过滤会把它们**静默丢掉**——没有异常、没有日志，只是数据消失了。

**正确判据：只排除已知 legacy 别名集合**（正则见 §8.9 强制方案 B）。排除它们是安全的，因为 AppKit 会从对应现代 UTI 自动合成回来（本测试 ② 已证）。

**注册行为汇总：** 尝试为上述 12 个标识符逐个注册 provider，最终**声明成功 12 个**，其中 5 个 legacy 被静默拒绝，但 `NSStringPboardType` 与 `Apple HTML pasteboard type` 仍出现在结果中——由 AppKit 从 `public.utf8-plain-text` 与 `public.html` 自动合成。
